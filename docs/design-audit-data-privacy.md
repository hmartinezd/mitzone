# Design audit: data contracts and privacy

Date: 2026-11-03. Static repository review for the approved design phase. No services, credentials, remote projects, or runtime datasets were accessed; no Flutter/backend code was changed. Checked-in migrations describe intended contracts, not proof of deployment or effective production permissions. Findings require validation against an isolated test backend before implementation acceptance.

## Supabase Backend Engineer findings

### Runtime data inventory

`productionModeProvider` means an authentication repository is configured, **not** that `APP_ENV` is production ([auth providers](../lib/core/auth/auth_providers.dart)). Development and staging can therefore use the same remote paths. Verify the target project before launching any runtime audit. Normal environment parsing requires development/staging/production and Supabase configuration; local compatibility is available through explicitly constructed/test configuration ([configuration](../lib/core/config/app_config.dart), [environment](../lib/core/config/app_environment.dart)).

### Contract questions to resolve before visual sign-off

1. **High: external discovery and policy alignment.** Checked-in runtime calls Google Places and Ticketmaster through Edge Functions ([places](../supabase/functions/nearby-discovery/index.ts), [events](../supabase/functions/nearby-events/index.ts)). `docs/legal-readiness.md` says these are not current recipients. Treat that as a documentation discrepancy; deployment is unverified. Design location disclosure and provider/source attribution against the actual intended runtime.
2. **High: reporting permission verification.** [0021_reports](../supabase/migrations/0021_reports.sql) revokes all authenticated table privileges and creates an insert RLS policy without an explicit insert grant in that migration. RLS policy alone does not confer table privileges. Verify effective grants in a test database before presenting reporting as operational; no fix is authorized in this phase.
3. **High: navigation must fit actual contracts.** A Groups destination has no established domain/repository in the inspected feature inventory. Nearby should describe bounded derived encounter context, not live map positions. Never promise new backend behavior through a mockup without marking it a proposal requiring approval.
4. **Medium: historical event context.** Runtime event catalog is populated from nearby fetches, while joined IDs and connection context may outlive that catalog. Design an honest unavailable/context fallback; do not assume every historical event can be rehydrated.
5. **Medium: notification documentation contradicts itself.** [Notifications foundation](notifications_foundation.md) initially calls push out of scope, then describes implemented FCM/webhook foundation. Distinguish repository implementation from unverified deployment, APNs/FCM configuration and actual delivery.

## Privacy & Security Reviewer findings

### Existing boundaries to preserve

- OS foreground-location permission and product presence consent are distinct. Presence activation calls `record(consent: ...)`; discovery uses a separate one-shot foreground observation and does not create presence evidence ([presence service](../lib/features/encounters/data/foreground_presence_service.dart), [discovery location](../lib/features/discovery/data/discovery_location_provider.dart)).
- Presence RPC assigns authenticated ownership and server time, converts coordinates to coarse cells and does not store/return raw coordinates; stop removes unexpired geolocation evidence ([0014](../supabase/migrations/0014_foreground_presence.sql), [0016](../supabase/migrations/0016_stop_foreground_presence.sql)). The client transmits raw coordinates to the trusted backend for resolution; copy must not imply no coordinate transmission.
- Profile hardening restricts owner records and uses a public-profile boundary; do not broaden reads to make mockups look richer ([0017](../supabase/migrations/0017_profile_privacy_hardening.sql), [public-profile repository](../lib/features/profile/data/supabase_profile_repository.dart)).
- Blocking terminates requests/relationships and gates conversations/messages; unblocking cannot resurrect the old relationship ([0025](../supabase/migrations/0025_permanent_relationship_termination.sql)). Preserve this behavior and participant reauthorization.
- Account deletion authenticates the requester before administrative deletion ([function](../supabase/functions/delete-account/index.ts)); notification webhook uses dedicated authentication ([webhook auth](../supabase/functions/dispatch-push/webhook_auth.ts)). No design phase should change these paths.

## Evidence and validation boundary

This is a design-input review, not a penetration test, legal review, database permission certification, retention audit or screenshot verification. Runtime availability, deployed migration parity, FCM delivery, effective grants, RLS behavior, account cascades, location lifecycle and real datasets remain unverified. Preserve existing tests and security boundaries. Use dedicated accounts and an explicitly identified isolated backend for later screenshots; simulated coordinates must be labeled and must not become real-world presence claims. Real user messages, report text, contact details, precise coordinates, secrets and tokens must not appear in review artifacts. No commits, pushes, deployments, production writes or backend changes are authorized.
