# Whole-app screen and state inventory

Status: source audit, 2026-11-03. Design proposals and runtime verification remain pending. Owner authorized whole-app audit and documentation, not application changes. “Implemented” below means a branch/control exists in source, not that it was exercised against live services. No app, emulator, tests, or network services were run for this inventory.

## Coverage and evidence

Routing authority: `lib/app/router/app_router.dart` and `app_routes.dart`. All 25 registered GoRoute destinations are listed below (including the development showcase). Startup failure and unknown-route handling are additional non-route surfaces. Shared navigation is `StatefulShellRoute.indexedStack`, with Home / Events / Matches / Chat / Profile branches. Notifications is a root route outside that shell. Nested event, match, chat, and profile routes remain inside their branches.

Presentation files were inspected across auth, onboarding, splash, home, events, encounters, matches, profile, personality, chat, notifications, navigation and foundation. Supporting state/interaction evidence comes from existing `test/features/`, `test/app/router/`, and design documents. Existing tests were read, not rerun; their existence is not current pass evidence. No pixel fidelity, actual screen-reader behavior, device permissions, provider availability or backend correctness is certified here.

Cross-check with [backend/privacy contracts](design-audit-data-privacy.md) and [Flutter/QA evidence](design-audit-flutter-qa.md). Configured remote mode is not proof of a production environment: inspect the actual target separately. Avatar files are currently local storage, public identity access is restricted, and report grants/deployed provider behavior require verification. Do not promise portable photos, richer identity, or successful safety submissions merely because the UI has a branch for them.

In each row, the final column lists design/verification work still needed, not approved new requirements. All rows require baseline emulator evidence, compact-screen/large-text review, and review of focus, semantics, safe areas and navigation.

## Journey coverage

| Journey | Existing path | Design-critical branches |
|---|---|---|
| First use → account → Home | Splash → onboarding → login/signup → entry resolver → Home | Interrupted onboarding; save failure; email confirmation; duplicate submit; unavailable auth/profile; session restoration |
| Password recovery | Sign in → request email → external link → reset → sign in | Generic confirmation; invalid/expired link; wrong session; cancel; password rejection; lost network |
| Decide where to go | Home discovery → event detail → join → Events Joined / Profile activity | Location unavailable; one provider fails; no images/results; informational place has no destination; source link; leave; direct versus Home back |
| Voluntary presence → encounter | Home → consent → OS permission → locating → recording → limited discoverability → Matches | Consent declined; GPS/server failure; expiry; Stop success/failure; app restart; provider-only discovery must not write presence |
| Encounter → connection | Matches → person → Say Hi → outgoing / incoming → Accept or Not now → connection | Profile/context missing; blocked; request errors; dependent loading; removal; privacy limits |
| Connection → conversation | Matches/person or Chat → get/create conversation → message list → send | Empty thread; generic identity; no network; unsent text; revoked/removed/blocked conversation; notifications target |
| Profile enrichment | Profile → Edit / Details / Social style → save → Profile/Home updated | Optional fields; avatar failure; validation; duplicate save; unsaved back; missing saved personality answers |
| Safety and account exit | Person → report/block/remove; Settings → privacy/unblock; account → sign out/delete | Expired encounter still needs safety access; ambiguous block list; mutation failures; deletion confirmation and outcome |
| Notification handling | Chat badge or push → Notifications / target | Mark-read failure; stale/deleted target; foreground/background/cold-start; auth restoration; request review |

## Explicitly absent product destinations

Explore, Nearby radar, Groups, group details/membership/creation, QR scanning, a dedicated connection-management destination, and a support/contact destination are not registered routes. Some may be future concepts, not missing implementations within approved scope. They require owner product decisions, data/backend feasibility, privacy review and separate implementation approval. Onboarding currently mentions QR codes despite no scanner route. Do not populate future concepts with invented people, activity or location evidence.

## Evidence to collect in the later approved visual phase

For every screen ID, track `baseline capture → proposal revision → owner approval → implementation → QA capture`, plus viewport, platform, text scale, environment/data source and reproduction path. Use real authorized test accounts and actual provider records for live-flow evidence; label deterministic edge-state fixtures separately. Do not run presence, join, messaging, sign-in or deletion against production for design screenshots. Screenshots are insufficient to prove semantics, privacy, backend authorization or screen-reader usability.
