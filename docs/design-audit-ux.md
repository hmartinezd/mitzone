# Whole-app UX/UI audit

Status: proposal for review, 2026-11-03. Lead responsibility: Senior Mobile Product Designer, delegated as a native Codex subagent. This is a source-based product audit, not a visual-fidelity certification. Application code, backend code, navigation and working features were not changed. See [screen/state inventory](design-audit-screen-inventory.md) for full route/journey coverage and limitations.

Specialist evidence: [backend/privacy review](design-audit-data-privacy.md), [Flutter/QA review](design-audit-flutter-qa.md). Consolidated review entry point: [audit overview](design-audit.md); coordinated direction and IA proposal: [design system and IA](design-system-and-ia-proposal.md). These documents are complementary; the priority table below identifies product responses to their source findings without certifying deployed behavior.

The product's strongest differentiator is reconnecting people through shared real-world context. Existing architecture already supports significant account, discovery, participation, presence, encounter, connection, chat and safety behavior. A professional redesign must make this coherent across the whole lifecycle, rather than polishing Home while consequential supporting states stay unfinished.

## Prioritization

P0 = privacy/trust or release-critical experience requiring resolution before public release; P1 = materially blocks or confuses a core journey; P2 = coherence, accessibility or polish work requiring design and verification. These priorities do not authorize code changes. “Risk” denotes a source-based concern requiring runtime reproduction; missing visual states are directly observed in source.

## Preserve and build on

- Home already distinguishes permission denial, permanent denial, disabled services, unavailable location, timeout, remote failure and actual empty discovery. Partial provider success stays visible. Preserve this coverage and informational-place semantics.
- Presence has explicit consent, separate locating/recording feedback, coarse context, expiry, and Stop. Improve visibility and failure states without widening data collection.
- Auth/recovery has safe failure messages, confirmation flows, duplicate-submit protection and guarded recovery state. Existing tests cover many of these branches; preserve them.
- Profile forms have validation, normalized optional lists, save protection and avatar rollback handling. Shared widget, contrast, responsive, route and domain tests already exist.
- Use current photographic provider images and required credit, with honest missing-image placeholders. Lack of usable provider photos is an integration/content constraint, not permission to fill a live screen with stock imagery.

## Design-system gaps and proposed direction

Existing foundations are in `lib/app/theme/` and `lib/shared/widgets/`; `VisualSystemShowcaseScreen` should remain the implementation reference after future approved changes. This audit proposes specifications, not a second component library.

| Area | Existing foundation / gap | Proposal for visual review |
|---|---|---|
| Color | AppColors, ColorScheme and semantic extension exist; Home/presence add independent values | One semantic surface ladder (canvas, panel, elevated, interactive), primary blue/cyan roles, muted text, border, focus and feedback; assess actual text/icon/state contrast on every surface |
| Type | Shared Material-style scale exists; Home overrides 42px headline and tracking | Display, page, section, card, body, metadata and control roles; choose typeface only after visual review; dynamic text and long-name examples |
| Layout | Spacing scale, max widths and 48px target token exist; mixed scaffolds and local padding | Shared page/header/inset rules, compact/standard phone layouts, landscape behavior, scroll and keyboard rules; keep meaning and actions at 2× text |
| Components | Buttons/cards/fields/banners/empty states/loading/dialogs exist; native widgets mixed with bespoke compositions | Document variants and all interaction states; semantic actionable versus informational cards; consistent retry and destructive-action patterns |
| Imagery | Real event HTTPS images, source credit and missing-photo handling; Places photo integration absent | Approved crop/overlay/credit/fallback system; support image-free cards as first-class designs; no invented real-world content |
| Social identity | Profile avatar exists; production chat/blocked entries generic | Authorized identity presentation with loading/deleted/redacted fallbacks, context chips and confidence-preserving relationship labels |
| Async and feedback | Strong Home/Profile patterns; inconsistent other screens | State templates for first load, partial load, stale data, empty, filtered-empty, denied, offline/error, retry, submitting, success and expired access |
| Motion/accessibility | Some reduced-motion and text-scale tests exist | Focus order and labels; live announcements; non-color status cues; reduced-motion rules; TalkBack/VoiceOver validation; no radar that implies precise person coordinates |
| Content | Premium real-world-social positioning documented; event/demo/technical language persists | Shared glossary for discover, join, presence, encounter, request, connection and conversation; consistent action labels and permission explanations |

## Information architecture alternatives

All are proposals requiring approval. Existing destinations remain until an explicitly approved migration.

| Option | Navigation and mapping | Trade-offs |
|---|---|---|
| A — retain current structure for first complete visual pass | Home / Events / Matches / Chat / Profile; improve labels/context within existing routes | Lowest functional risk and fastest complete-app design baseline; Events/Matches labels continue emphasizing event participation and may feel narrower than product positioning |
| B — consolidate around current capabilities | Home / Explore / Connections / Chat / Profile; Explore would map current event/places discovery, Connections would organize encounters, requests and existing connections | Better real-world-social vocabulary; preserves prominent messaging; requires explicit taxonomy, route/back/deep-link mapping, and decisions about informational places; renaming is still a navigation change |
| C — documented long-term vision | Home / Explore / Nearby / Groups / Profile, persistent messages and notification access; Events inside Explore, encounters/requests within a carefully defined Nearby/social flow | Strongest match to documented direction; Groups and radar concepts lack implemented destinations/contracts; largest new scope, privacy/accessibility risk and hidden Chat risk; requires product/backend approval before detailed interactions are treated as buildable |

Recommendation: use A as the truthful baseline and visual coverage anchor. Present B alongside it for an owner IA decision. Keep C as a separately scoped future concept until Groups, Nearby semantics and persistent Chat access have explicit requirements. A complete professional visual design can cover current capabilities without silently adding future ones.

## Proposed professional visual-design phase

This phase requires owner approval before it starts. Deliver actual inspectable screen designs, not only prose. Use an agreed design authoring format with editable sources and exported PNG/PDF review boards; no Figma connection is assumed. A standalone local review board can display exports and state links, without modifying Flutter application code or becoming a new product website.

1. Resolve IA vocabulary, target user priorities, dark-theme foundation, and trust copy. Gather available reference images; existing docs are direction, not pixel-level approval. Mark speculative future capabilities separately.
2. Produce a visual direction board and component board: palette/type/layout, actionable/informational image cards, identity, navigation, form controls, status/retry and destructive dialog examples. Include image-free and 2× text examples, not only ideal hero images.
3. Produce complete primary-screen mockups for all inventory IDs. Batch review by connected journeys: entry/account/recovery; Home/discovery/event/presence; encounter/requests/person/safety; connections/chat/notifications; Profile/enrichment/settings/legal. Include actual overlays and important failure/empty/permission states in each batch.
4. Link the mockups into a clickable journey prototype where the chosen tool supports it. Provide compact and standard phone variants, a 2× text stress board, keyboard/dialog states, long names, missing photos, and data provenance. Use authorized sanitized real records where available; hypothetical layout samples must be visibly labeled, never presented as live provider proof.
5. Record owner decisions per screen/state ID and design revision. Approval includes copy, interaction and visual hierarchy, not only a contact sheet. Unresolved backend/privacy questions stay visible; owner approval does not prove technical feasibility.
6. Before implementation, Flutter and backend specialists check feasibility and data contracts; privacy reviews disclosure/safety; QA turns each approved state into an acceptance scenario. The later Flutter implementation must be approved separately, in manageable batches.
7. After authorized implementation, compare actual emulator screenshots against approved exports at matching viewport/text scale. Track deviations to resolution; screen-reader and interaction tests supplement images. Never mark source audit or mockups as runtime validation.

Completion criterion for product-design work: every current inventory screen, relevant state and journey has a reviewed design or an explicitly accepted unchanged treatment; components/tokens are documented; navigation/data/privacy decisions are resolved; visual sources and exports are available; unresolved questions are tracked. Future Groups/Explore/Nearby feature design is included only to the scope the owner explicitly approves.
